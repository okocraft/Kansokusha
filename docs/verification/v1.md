# v1 verification

Use Java 25 and run the following from a clean checkout:

```shell
./gradlew clean verifyV1
```

`verifyV1` depends on the normal Gradle `build` lifecycle. The build runs the
repository unit tests and the packaged Paper and Velocity integration checks wired
into each platform's `check` task. After the build completes, `verifyV1` inspects
the final distribution artifacts copied to the root `build/libs` directory.

For the current project version, the task requires both of these files:

- `Kansokusha-Paper-<version>.jar`
- `Kansokusha-Velocity-<version>.jar`

Each final jar is opened directly. Verification requires the shaded
`org/duckdb/DuckDBDriver.class` runtime class and the platform descriptor. The Paper
artifact must contain `paper-plugin.yml` with the expected plugin name, resolved
version, main class, API version, and Folia support flag. The Velocity artifact must
contain `velocity-plugin.json` with the expected plugin id, name, resolved version,
and main class.

The packaged integration checks provide the runtime side of descriptor verification:
Paper and Velocity each start with their shaded artifact, exercise the external API,
perform normal shutdown, and verify the persisted fixture event. The final artifact
inspection additionally checks that the jars copied for distribution are the expected
named outputs and still contain the required runtime and descriptor entries.

GitHub Actions invokes `verifyV1` from a fresh checkout and uploads the verified
`build/libs` directory. This workflow only builds, tests, verifies, and uploads CI
artifacts; it does not publish a release or deploy the plugin.

Resource measurements remain explicit commands because they report observations
rather than acceptance criteria:

```shell
./gradlew :kansokusha-common:measureThroughput
./gradlew :kansokusha-common:measureBoundedBuffer
```

See `docs/throughput-measurement.md` for their parameters and limitations.
