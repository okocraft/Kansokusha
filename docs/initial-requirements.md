# Kansokusha v1 要件定義

## 1. 目的

Kansokusha は、OKOCRAFT の Minecraft サーバー上で発生する活動・状態変化を、ゲーム処理への影響と保存容量を抑えながら長期間記録するためのログ基盤とする。

CoreProtect のログ記録部分と用途は近いが、以下は目的としない。

- CoreProtect API との互換性
- CoreProtect の完全な代替
- CoreProtect より高い性能を示すこと自体

Kansokusha の目的は、OKOCRAFT の実運用に適した機能性・保持方針・拡張性を持つログ記録基盤へ刷新することである。

## 2. 対象環境

以下を対象とする。

- Paper / Folia
- Velocity

各サーバー・プロキシは独立したログストレージを持つ。

Paper サーバー間、および Velocity を含むネットワーク全体の横断検索・集中管理は初期要件に含めない。

## 3. v1 のスコープ

v1 は、ログの記録と保持管理の基盤に集中する。

v1 で必要とする機能は以下とする。

- イベントを受理できること
- イベントを永続化可能なログデータへ変換できること
- ゲーム処理を不必要にブロックせずログを蓄積できること
- DuckDB にログを永続化できること
- イベントの性質に応じた保持期間を設定できること
- 保持期限を過ぎたデータを削除できること
- 外部プラグインが独自の event type を登録できること
- 外部プラグインが独自イベントを記録できること

## 4. v1 の非対象

以下は v1 の必須要件に含めない。

- ログ検索コマンド
- ログ検索 UI
- 公開検索 API
- rollback / restore
- Web UI
- ネットワーク全体の横断検索
- CoreProtect API compatibility
- 全 Minecraft イベントへの完全対応
- 高度な因果関係追跡
- 完成された coalescing policy
- 異常なイベント流量に対する高度な overload / drop / backpressure policy

## 5. 記録対象

Minecraft サーバー上の監査・調査に有用な活動および状態変化を記録可能にする。

ただし、以下は基盤要件とは分離し、別途イベントカタログとして定義する。

- 具体的にどのイベントを記録するか
- 各イベントでどの情報を保存するか
- 各イベントをどの程度の粒度で保存するか
- 各イベントをどの程度の期間保持するか
- 中間状態をどこまで保持または省略するか

v1 では、基盤を検証するための最低限の組み込みイベントのみを必須とする。

## 6. 状態変化の圧縮

自然変化など一部のイベントでは、中間状態を完全に保持しないことを許容する。

例えば、

```text
AIR -> WATER(level=7) -> WATER(level=6) -> WATER(source)
```

という状態遷移を、

```text
AIR -> WATER(source)
```

として記録してよい。

ただし、具体的にどのイベントを coalescing 対象とするか、どの時間幅でまとめるか、どの中間状態を保持するかは別途決定する。

## 7. Event Type

### 7.1 外部登録

外部プラグインが独自の event type を登録できること。

event type の公開識別子は、以下のような namespace 付きの安定した識別子とする。

```text
namespace:key
```

Paper API 上では `NamespacedKey` と自然に接続できる形が望ましい。

### 7.2 永続識別

ストレージ内部では保存効率のため、event type を整数 ID 等へ変換してよい。

ただし、以下を満たすこと。

- 永続データから元の namespace 付き識別子を復元できること
- event type の識別情報は永続的に保持されること
- event type を提供した外部プラグインが削除されても識別情報を失わないこと
- 同じ key が後から再登録された場合、過去ログと同じ event type として扱えること
- runtime の event registration と永続的な event type registry を分離できること

## 8. Event Payload

外部プラグイン固有の payload について、Kansokusha 自身が内容を理解する必要はない。

Kansokusha が共通で記録できる情報として、少なくとも以下を想定する。

- event type
- 発生時刻
- サーバー
- 必要に応じてワールド
- 必要に応じて位置
- 必要に応じてプレイヤー等の主体
- retention に必要な情報
- event 固有 payload

event 固有 payload の意味の解釈は、その event type の提供側の責任とする。

payload の形式変更に対応できるよう、同一 event type の payload format を世代管理できること。

## 9. Retention

すべてのイベントを同じ期間保持する必要はない。

イベントの重要度・性質に応じて保持期間を変更可能とする。

例えば、

- 監査価値が高いログは長期間保持する
- 高頻度で長期的価値の低いログは短期間で削除する

といった運用を可能にする。

以下を満たすこと。

- retention policy を設定できること
- event type と retention policy を関連付けられること
- 期限切れデータを自動的に削除できること

具体的な retention class 名、保持期間、各 event type との対応は別途決定する。

## 10. ストレージ

初期ストレージ実装として DuckDB を使用する。

DuckDB JDBC 等の必要な実行時依存は最終成果物へ shade し、追加の手動インストールを不要にする。

DuckDB を v1 のストレージ実装として使用する。

## 11. パフォーマンス

Kansokusha によるログ記録がゲーム処理へ与える影響を小さくすること。

少なくとも以下を満たすこと。

- Paper / Folia / Velocity のゲーム処理スレッド上でストレージ I/O 待ちを発生させないこと
- ログ処理によるメモリ使用量が通常運用下で無制限に増加しないこと
- 書き込みを効率的にまとめられること
- ログ記録処理の性能を後から測定できること

測定対象として、少なくとも以下を想定する。

- events/sec
- CPU 使用量または CPU time
- メモリ使用量
- 書き込み量
- ディスク使用量

v1 では絶対的な性能目標値を設定しない。

CoreProtect との比較結果も acceptance criteria にはしない。

通常運用では writer が追いつかないケースを想定しないため、writer saturation 時の高度な overload policy は v1 の要件外とする。

## 12. メモリ使用量

ログ処理によるメモリ使用量は有限でなければならない。

通常運用下で、未永続化ログや内部バッファがイベント数に比例して無制限に増加し続ける設計としてはならない。

具体的な上限値や制御方式は設計・実測段階で決定する。

## 13. Durability

Minecraft のワールド状態自体がクラッシュ時に完全保存される保証はないため、ログだけに非常に強い durability guarantee は要求しない。

以下を要件とする。

- 正常停止時には、受理済みログを可能な限り永続化してから終了すること
- JVM crash、OS crash、強制終了等により直近の未永続化ログが失われることを許容する
- 既に正常に永続化されたログを不必要に破損させないこと
- ストレージへの書き込み失敗を無言で無視しないこと
- 記録不能になった場合、管理者がサーバーログ等から認識できること

## 14. 機密情報

Kansokusha 独自の redaction、秘密情報除去、機密情報フィルタリングは v1 では要求しない。

command、chat 等について、記録対象とした内容はそのまま保存してよい。

## 15. アップグレードとデータ互換性

Kansokusha のアップデートによって、既存の正常なログデータを理由なく破棄してはならない。

ストレージ schema、event metadata、その他の永続形式を変更する場合、既存データを継続利用できる migration path を用意できること。

具体的な migration 方式は設計段階で決定する。
